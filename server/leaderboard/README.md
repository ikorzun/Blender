# Своя таблица лидеров — сервер (Cloudflare Worker + D1)

Реализация серверной части по постановке `docs/LEADERBOARD-OWN.md`.
Клиент (`src/app/82-lb.js`) — отдельная задача, ядро игры не правится.

## Зачем своя, а не платформенная

Сервер площадки хранит **максимум** и понижать не умеет. Владельцу нужна
«Форбс»-модель: потратил очки — упал в списке. Поэтому здесь пишется
**последнее** значение `leaderboardScore()`, а не лучшее.

## Прогон

```bash
node server/leaderboard/test/run.js
```

```bash
node server/leaderboard/test/break.js
```

Первый — 24 стража на **настоящем SQL** (`node:sqlite`, зависимостей не
добавляет): оконная функция лесенки, частичный индекс, тай-брейк, keyset-соседи
проверяются поведением базы, а не моком. Второй — обязательная по канону
двусторонняя проверка: 8 диверсий, каждая обязана уронить **свой** ассерт.

## Эндпоинты

| | | |
|---|---|---|
| `POST /v1/score` | `{id,k?,n,a,s,q,t,sig}` | upsert + ОЦЕНКА места (`rank` может быть `null`) |
| `GET /v1/top?p=1` | — | топ из снимка, кэш 60 с |
| `GET /v1/me?id&t&sig` | — | точное место + 5 соседей сверху и снизу |
| `DELETE /v1/me?id&t&sig` | — | удаление своей строки |
| `POST /admin/hide` | Bearer | скрыть/вернуть строку руками |

Коды: 400 форма/часы, 401 подпись, 409 повтор `q` (идемпотентно, с
сохранённым состоянием), 429 чаще 20 с, 503 сбой.

⚠️⚠️ **`rank` В ОТВЕТЕ НА ОТПРАВКУ — ЭТО ГРАНИЦА «НЕ ЛУЧШЕ N», А НЕ МЕСТО, И
`null` ЗАКОННЫЙ ОТВЕТ.** Оценка считается по лесенке (счёт на каждом сотом
месте) и стоит ноль обращений к базе — ради этого лесенка и заведена. Границы
нет в двух случаях, и оба отдают `null`:
* в таблице меньше сотни игроков — лесенка пуста (это состояние первых недель
  после запуска);
* счёт выше первой ступени — известно лишь «где-то в первой сотне».

⛔ **Точное место живёт ТОЛЬКО в `/v1/me` (`exact: 1`). Экран обязан брать
место оттуда, а не из ответа на отправку.** Здесь стояла уверенная `1`, и
формально контракт был честен — рядом едет `exact: 0`. Но поле называется
`rank`, и первый же живой потребитель прочёл его как настоящее место: значение,
которое нельзя перепутать, лучше пометки, которую можно не заметить.

⚠️ **Тело ответа всегда непустой JSON, успех — полем тела.** Если однажды
пойдём через транспорт бриджа, он делает `fetch().then(r=>r.json())` без
проверки `res.ok`: пустое тело приезжает как провал, а 500 с телом — как успех.

⚠️ **Запросы «простые» по CORS** — тело `text/plain`, никаких кастомных
заголовков: иначе каждая отправка стоила бы ДВА запроса из суточных 100 000.
Единственное исключение — `DELETE /v1/me`: метод не входит в простые, и
предполётный запрос неизбежен. Это осознанно — удаление своих данных
случается раз в жизни и не лежит на горячем пути.

## Деплой

```bash
npx wrangler d1 create blendo-lb
```

Полученный `database_id` вписать в `wrangler.toml`, затем:

```bash
npx wrangler d1 execute blendo-lb --remote --file=server/leaderboard/schema.sql
```

```bash
npx wrangler secret put ADMIN_TOKEN
```

```bash
npx wrangler deploy --config server/leaderboard/wrangler.toml
```

Первый снимок появится в ближайший час — крон-триггером.

⚠️⚠️ **РЕЦЕПТ «форснуть снимок через `wrangler dev --test-scheduled`» УБРАН
КАК НЕПРОВЕРЯЕМЫЙ.** `wrangler dev` без `--remote` поднимает ЛОКАЛЬНЫЙ воркер
с ЛОКАЛЬНОЙ D1 — боевой снимок он не строит, а оператор при этом уверен, что
форсанул. Ровно та асимметрия `--remote`, которую README знает для
`d1 execute`. **Живьём не проверялось** (нужен аккаунт Cloudflare), поэтому в
чек-листе оставлен единственный путь, который проверяется наблюдением:
дождаться часового тика и прогнать смоук ВТОРОЙ раз — живость крона
доказывает сдвинувшееся поле `t` в ответе `/v1/top`.

Понадобится форс до релиза — это отдельная правка воркера (`POST /admin/snap`
под тем же Bearer). Сознательно НЕ делаем накануне одноразового захода в
чужой аккаунт: риск правки больше закрываемого.

⚠️ **Из дашборда руками — правило Cloudflare Rate Limiting по IP** (WAF, на
`/v1/score`). Это пункт 3 защиты из постановки, и он единственный, который
воркер за себя не заводит: наше окно 20 с живёт в поле `u` строки игрока и
защищает ОДНУ строку, а не адрес. Сам IP при этом не храним.

## Деградация: что сделано и что нет

- `/top` при недоступной D1 отдаёт **200 с пометкой `stale`**, а не 503 —
  правило номер один постановки: таблица украшение и игру не блокирует.
  Страж на это есть (база, кидающая исключение на каждом запросе).
- ⛔ **Кэш края (`caches.default`) как хранилище последнего снимка НЕ
  реализован.** В постановке он назван, но проверить его в Node нечем —
  Cache API живёт только в рантайме воркера. Сейчас при упавшей D1 экран
  получает пустой список с честным `stale:1` и рисует своё состояние
  «нет связи» (у него для этого есть локальный кэш и своя строка из
  баланса). Если владельцу нужен именно серверный stale — это отдельная
  правка и живой смоук после деплоя, молча она не проверяется.

## Локальный стенд для разработки клиента и экрана

Пока боевой воркер не развёрнут, клиент (`src/app/82-lb.js`) и экран
разрабатываются против постоянного стенда:

```bash
node server/leaderboard/test/dev-serve.js
```

Порт 8788 (у превью игры 8779, у `wrangler dev` 8787 — не пересекаются).

⚠️⚠️ **ИГРА САМА В СТЕНД НЕ ЦЕЛИТСЯ — ВКЛЮЧАТЬ ЯВНО:** откройте превью с
`?lb=1` (или `?lb=<адрес>`, или положите адрес в `localStorage.mixer_lb_url`).
Раньше клиент включался на ЛЮБОМ `localhost`, но на localhost сидят все
направления сразу: у Графики, Физики и Повествования стенда не поднято, и они
получали неудачные запросы в консоли на каждой победе, без намёка почему.
Тот же `src/index.js` поверх `node:sqlite`, живёт до Ctrl-C. При старте
засевает 24 строки с ЖИВЫМИ именами и разбросом счёта по порядкам (в списке
есть и пятизначные, и двузначные — на ровном ряду не видно, как вёрстка
держит длинные числа) и **сразу строит снимок**, поэтому `/v1/top` отдаёт
непустой список с первой секунды.

⚠️ Среди сида есть одна **скрытая** строка `ShouldNotAppear` — экран обязан её
не показывать, и проверить это можно только если она в базе есть.

| маршрут стенда | зачем |
|---|---|
| `POST /_dev/snap` | построить снимок — на боевом это делает крон раз в час, локально крона нет вовсе |
| `POST /_dev/seed?n=24` | пересеять список |
| `POST /_dev/rewind?sec=3600` | состарить строки: досрочно открывает окно частоты (20 с) |
| `POST /_dev/reset` | очистить |
| `GET /_dev/state` | что сейчас в базе и в топе |

⚠️ **«МОЯ СТРОКА ПРОПАЛА ИЗ ТОПА» БОЛЬШЕ НЕ ЖДЁТ ВАС НА СТЕНДЕ.** Здесь стояло
предупреждение: сервер резал рост по возрасту строки и прятал её, а снаружи
это читалось как поломка клиента (поймано прогоном стенда, стоило бы полдня
следующему). Механики нет с 2026-08-09 — оставляю след, чтобы объяснить, чего
именно тут больше не случится.
Сегодня строка исчезает из общей таблицы **только** от ручного `/admin/hide`;
в сиде такая одна — `ShouldNotAppear`. Единственный оставшийся отказ сервера —
`429` по окну частоты, и он лечится `POST /_dev/rewind`.

⚠️ **Маршрутов `/_dev/*` в боевом воркере НЕТ и не будет** — они живут только
в `dev-serve.js` и перехватываются до обращения к воркеру. Причина та же, по
которой отложен `/admin/snap`: продукт накануне одноразового захода в чужой
аккаунт не трогаем.

⚠️ База **в памяти**: перезапуск стенда = свежий сид, отправленные строки
не переживают рестарт. Для разработки экрана этого достаточно; понадобится
устойчивость — скажите, добавлю файловую базу.

## Смоук после деплоя — по списку, а не по памяти

```bash
node server/leaderboard/test/smoke.js https://lb.<домен>/
```

⚠️ **Это скрипт, а не список прозой** — намеренно: чек-лист текстом никто не
исполняет, и в день доступа выясняется, что половина шагов неисполнима.
Тот же сценарий гоняется локально и уже зелёный:

```bash
node server/leaderboard/test/smoke.js --local
```

На боевом воркере проверок **одиннадцать** (локальный прогон добавляет две —
показ жёлтого состояния и переход в зелёное после постройки снимка).
Зелёным считается ровно это:

| шаг | зелёный ответ |
|---|---|
| отправка результата | `200`, `ok:1`, место в теле, **`s` равен отправленному** |
| повтор той же отправки | `409` c `dup:1`, счёт тот же |
| вторая запись сразу | `429` — окно 20 с держит |
| битая подпись | `401` |
| чтение топа | снимок СВЕЖИЙ: `stale` нет, `t` моложе 2 ч |
| своё место | `200`, `exact:1`, соседи массивом, счёт тот же |
| заголовок ACAO на чтении | `*` |
| предполёт для DELETE | `204` + `allow-methods` содержит `DELETE` |
| вторая УСПЕШНАЯ отправка | счёт изменился **в перечитке `/v1/me`** |
| удаление своих данных | `200`, `gone:1` |
| чтение после удаления | `404` |

⚠️ **ЖЁЛТЫЙ ИСХОД — НЕ ЗЕЛЁНЫЙ И НЕ КРАСНЫЙ.** Если топ отдаёт `stale:1` или
`t:0`, снимок ещё не строился: на свежем деплое это нормально (крон печёт раз
в час), но ОТ «крон не зарегистрировался и топ пуст навсегда» это неотличимо
до второго прогона. Скрипт в этом случае возвращает **код 2** и не печатает
«отвечает по контракту». **Протокол: дождаться часового тика и прогнать
смоук повторно** — живость крона доказывает сдвинувшееся `t`.
Прежняя версия проверяла только «200 и массив» и была зелёной на мёртвом
снимке; дока при этом тремя абзацами ниже объявляла пустой топ нормой, то
есть подсказывала не приглядываться ровно к тому сигналу, который различает
эти два состояния.

⚠️ Число строк в топе НЕ проверяется: в день деплоя игроков ноль, и пустой
СВЕЖИЙ снимок — здоровый ответ.

⚠️ Смоук занимает около 25 секунд: внутри честное ожидание окна частоты, без
которого путь `UPDATE` (вторая отправка) не исполняется вовсе, а именно он
несёт «Форбс»-модель — падение счёта.

### Если смоук оборвался

Строка `SMOKE` пишется в боевую таблицу. Скрипт убирает её тремя путями
(нормальный финал, `finally`, перехват Ctrl-C), но **гарантии нет**: при
жёстком убийстве процесса или обрыве сети на самом удалении она останется, а
ночная ретенция её не заберёт (она чистит молчащие 180 дней). Поэтому id
печатается ПЕРВОЙ строкой прогона, ДО создания строки. Ручная уборка:

```bash
npx wrangler d1 execute blendo-lb --remote --command "DELETE FROM p WHERE id='<id из шапки прогона>'"
```

Если строка уже попала в снимок и видна игрокам — мгновенно убирается
`POST /admin/hide` с Bearer, не дожидаясь следующего крон-тика.

## Что честно сказать про защиту

⛔ **ЗАЩИТЫ ОТ НАКРУТКИ ЗДЕСЬ НЕТ.** Решение владельца 2026-08-09, дословно:
«давай не будем мудрить и сейчас делать защиту от накрутки. Пока сделай
хорошую простую основу для лидерборда». Возрастной потолок доверия
(`GROW_BASE`/`GROW_PER_S`), тихая обрезка присланного счёта и автоматическое
скрытие подозрительной строки **удалены целиком**, а не выключены флагом:
история в git, возврат — `git revert`.

⚠️ **ЦЕНА НАЗВАНА ВЛАДЕЛЬЦУ И ПРИНЯТА.** Счёт считает клиент, сервер проверить
его не может. Значит любой, кто откроет консоль, пришлёт любое число и встанет
первым, не сыграв ни уровня. Это осознанный размен «простота сейчас» против
«честность таблицы», а не недосмотр и не забытая задача.

### Что осталось — и почему это НЕ «защита от накрутки»

Снести заодно — типичная ошибка, поэтому список явный:

| остаётся | что на самом деле защищает |
|---|---|
| подпись `sig` | **право собственности на строку.** Без неё посторонний перезапишет чужой результат и удалит чужие данные. Защищаем игрока от ПОСТОРОННЕГО, а не от него самого |
| `RATE_SEC = 20` | **наш бесплатный тариф** (лимит запросов к базе), а не честность. Снять — первый же цикл отправок съест суточную квоту |
| `/admin/hide` + флаг `f` | **ручная модерация.** Теперь она единственная: имя приходит с клиента как есть, и от непристойного имени в топе больше ничего не страхует |

⚠️ Флаг `f` в обработчике отправки **не трогается ни в какую сторону**.
Выставлять его стало некому (автоматики нет), а снимать отправкой — значит
позволить спрятанному руками вернуть себя первой же победой. Единственный
владелец флага — админ. На это стоит страж и отдельная диверсия.

⚠️ Поле `c` (когда строка создана) по-прежнему пишется, но механикой **не
читается** — на нём держался возрастной потолок. Оставлено для ручной
модерации: отличить свежую строку от давней иначе нечем.

## Смета

Строка чтения в D1 — **просканированная**, а не отданная. Поэтому точный
`COUNT(*) WHERE s > ?` для игрока на 30 000-м месте стоил бы 30 000 строк на
каждой отправке и в бесплатный тариф не влезает никогда. Отсюда лесенка:
cron раз в час собирает счёт на каждом сотом месте (при 50 000 игроков это
500 чисел), оценка места после отправки стоит **ноль** обращений к базе,
точное место — не больше сотни строк и только при открытии экрана.

До ~5 000 активных в сутки — бесплатный тариф с двукратным запасом;
50 000 активных — Workers Paid $5/мес без овераджей.
